# Self-Loop Rule — 기준 충족까지 자가 반복

> 품질 기준이 명확한 산출물은 **한 번에 끝내지 않는다.** 스스로 채점하고, 부족하면 스스로 고치는 루프를 돈다. 이 플러그인을 쓰는 **모든 프로젝트의 공통 규칙**이다. (경로 무관 — 항상 적용)

---

## § 1 — 언제 적용

| 상황 | 적용 |
|------|------|
| 명확한 합격 기준이 있는 산출물 (코드, GDD, PRD, 문서, 밸런스 데이터 등) | ✅ 루프 적용 |
| 사용자가 "될 때까지", "기준 충족까지", "루프 돌려", "/self-loop" 요청 | ✅ 루프 적용 (필수) |
| 스킬 게이트(`/smoke-check`, `/gate-check`, `/story-done` 등)에서 FAIL/CONCERNS 후 재작업 | ✅ 루프 적용 |
| 단순 사실 확인, 1줄 수정, 탐색성 질문 | ❌ 단독 1회 실행 |

명시적 실행은 `/self-loop` 스킬. 스킬 호출 없이도 위 조건에 해당하면 이 프로토콜을 기본 작업 방식으로 삼는다.

---

## § 2 — 루프 프로토콜 (매 회차 4단계)

```
루프 시작 전:
  - 무엇을 만들지 1문단으로 확정
  - 합격 기준 3~7개 확정 (엄격하게 — § 3 참조)

매 회차:
  1. 계획 — 이번 회차에 할 딱 한 가지를 말한다.
  2. 실행 — 결과물을 만들거나 고친다.
  3. 채점 — 기준마다 먼저 묻는다: "스크립트가 판정할 수 있는가?"
       예 → 실행하고 exit code 가 점수를 정한다. 내 판단이 뒤집지 못한다.
       아니오 → 그때만 1~10 점. 후하게 주지 말고 부족한 점을 콕 집어 적는다.
  4. 판단 — 전 기준 8점 이상 → "완료" 선언 후 멈춘다.
       아니면 "계속" — 다음 회차는 제일 낮은 점수부터 고친다.

규칙:
  - 전 기준 8점을 넘기 전엔 절대 "끝냈다"고 하지 않는다.
  - 매 회차 직전에 제일 낮았던 기준을 먼저 고친다.
  - 사용자에게 되묻지 않고 스스로 판단해 진행한다 (§ 4 중단 조건 제외).
```

계약은 `docs/deterministic-gates.md` 와 같다 — `0` 통과 / `1` 경고 / `2` 중단 /
`3` 판정불가. **exit 3 은 통과가 아니다.** 돌지 못한 게이트는 판정을 낸 적이 없다.

## § 2.1 — 기본값은 고치기가 아니라 **보존**

§ 3 의 인플레이션이 "끝내고 싶어서 후하게 준다" 라면, 그 반대편에 **고치고 싶어서
멀쩡한 것까지 다시 쓰는** 함정이 있다. "최저 점수부터 고쳐라" 라는 지시만 있으면
모델은 근거 없이 그 영역 전체를 재작성한다. 최대 5회 상한은 이것을 막지 못한다 —
회차마다 착실히 뭔가를 고치면서 산출물이 계속 흔들리기 때문이다.

**결함 증거가 없으면 그 부분은 건드리지 않는다.** 채점자는 점수만 내는 것이 아니라
고칠 근거를 함께 내야 하고, 근거는 아래 4필드를 갖춘 **결함 티켓** 형태여야 한다.

| 필드 | 내용 |
|---|---|
| `claim_id` | 어느 기준·어느 부분인가 (파일:줄, 절 번호, AC 번호) |
| `defect_type` | 사실오류 / 기준미달 / 계약위반 / 누락 / 가독성 |
| `evidence` | 인용. 테스트 출력, exit code, grep 결과, 원문 대조 |
| `severity` | `보존` / `국소수정` / `전면재생성` |

`severity` 가 수정 폭을 정한다. **기본값은 `국소수정`이고, `전면재생성`은 결함이
구조 자체일 때만** 쓴다 — 티켓 3개가 나왔다고 문서를 새로 쓰지 않는다.

**채점자 우선순위 (위에서부터 시도):**

1. **결정적** — 스크립트 exit code. 여기서 판정되면 아래 둘은 쓰지 않는다.
2. **도구** — 린터·테스트·grep. 출력을 해석하지 말고 결과를 인용한다.
3. **모델** — 위 둘로 판정 불가능한 것만 (가독성, 어조, 논지의 성립 여부).

만드는 쪽과 채점하는 쪽이 같으면 자기 산출물을 방어한다. **heavy 루트에서는
채점을 별도 서브에이전트에 맡긴다** — 그 에이전트에게는 "무엇을 만들었는지" 가
아니라 **최종 상태와 기준만** 준다 (`rules/subagent-collaboration.md` § 3.1).

## § 2.2 — 회차 입력은 누적하지 않는다

2회차 이후 **전체 맥락을 다시 넣지 않는다.** 회차마다 컨텍스트가 불어나면 비용이
붙는 것은 물론이고, 모델이 과제 자체를 재해석해 이전 회차의 합의를 되돌린다.

재주입하는 것은 넷뿐이다:

```
- 직전 산출물 (또는 고칠 구간만)
- 이번에 처리할 결함 티켓
- 위반된 기준과 허용값
- 건드리지 말아야 할 것 (severity: 보존 항목)
```

`rules/route-hint.md` 의 610K vs 134K 측정과 같은 이야기다 — 그쪽은 쪼개서 공유
컨텍스트를 반복 로드한 경우이고, 이쪽은 회차마다 반복 로드하는 경우다.

## § 3 — 함정 1 방어: 자가 채점 인플레이션

루프가 잘 돌수록 위험한 첫 번째 함정 — **AI가 루프를 끝내고 싶어서 스스로 후하게 채점한다.** 방어:

- **기준은 검증 가능하게 쓴다.** "코드가 좋다" ❌ → "테스트 전부 통과 + 하드코딩 값 0개 + 에러 경로에 처리 존재" ✅
- **증거 기반 채점.** 8점 이상을 주려면 근거(테스트 출력, 실행 결과, 실제 파일 내용, grep 결과)를 **인용**해야 한다. 증거 없는 8점 이상 금지.
- **모든 점수에 "부족한 점" 1개 이상 명시.** 10점이라도 남은 리스크를 적는다. 쓸 게 없다는 것은 채점하지 않았다는 뜻이다.
- **상태 변경 코드가 대상이면** 전역 3대 버그 점검(race condition / partial write / idempotency)을 기준에 포함한다.

## § 4 — 함정 2 방어: 무한 루프 / 토큰 폭주

두 번째 함정 — **기준 미달이 계속되면 루프가 끝없이 돌며 토큰을 태운다.** 방어:

- **최대 회차 기본 5회.** (사용자가 다르게 지정하면 그 값)
- **2회 연속 무진전 시 즉시 중단.** 최저 점수가 2회차 연속 오르지 않으면 루프를 멈추고 보고한다: 현재 점수표 + 막힌 원인 + 시도한 접근 + 필요한 결정. 같은 접근의 3번째 반복은 금지 — 접근을 바꾸거나 사용자에게 넘긴다.
- **회차마다 진행 로그 1줄.** `[회차 N/5] 최저: <기준> <점수> → 이번 조치: <한 가지>` — 사용자가 루프 상태를 항상 볼 수 있게.

### § 4.1 — 실패를 분류한다: 반복할 것과 즉시 멈출 것

원인을 가리지 않고 5회를 채우는 것은 방어가 아니라 낭비다. 실패를 먼저 나눈다.

| 분류 | 예 | 처리 |
|---|---|---|
| **retryable** | 플래키 테스트, 일시적 네트워크·도구 오류 | 반복 대상. 회차 소모 |
| **hard_error** | 스키마 위반, 권한 거부, 정책 게이트 `exit 2`, 계약 위반 | **즉시 종료.** 같은 입력으로 다시 시도해도 결과가 같다 |
| **blocked** | 권한·데이터·사람의 결정이 없어 더 진행 불가 | **즉시 종료.** 실패가 아니다 |

### § 4.2 — 종료 유형은 셋이다

`완료` / `실패` 두 가지로만 끝내면, **더 돌 수 없어서 멈춘 상태가 실패로 기록된다.**
그 둘은 후속 조치가 다르다 — 실패는 고치는 것이고, 보류는 결정을 받는 것이다.

```
완료   전 기준 8점 이상 + 정책 게이트 exit 0
실패   회차 상한 소진 또는 2회 무진전 — 무엇이 막혔는지 보고
보류   BLOCKED. 권한·데이터·사람 판단이 없어 진행 불가.
       무엇이 있어야 재개되는지와 재개 지점을 명시한다.
```

**정책 축은 점수와 무관하게 단독 차단권을 갖는다.** 전 기준 10점이어도
`scripts/verify_policy.py` 가 `exit 2` 면 완료가 아니다 — 규칙을 어기고 도달한
기준 충족이 바로 unsafe-success 다 (`docs/deterministic-gates.md`).

## § 5 — 종료 보고 (완료든 중단이든 필수)

루프의 결과를 사용자가 **직접 검증할 수 있는 형태**로 보고한다. "이해는 위임할 수 없다" — 점수만 던지고 끝내는 것은 금지.

```
결과: 완료 | 실패(사유) | 보류(무엇이 있어야 재개되는가 + 재개 지점)
회차: N/5
정책 축: verify_policy.py → exit N   (판정 못 했으면 "미실행" — 통과로 적지 않는다)

| 기준 | 최종 점수 | 판정 주체 | 증거 | 남은 리스크 |
|------|-----------|-----------|------|-------------|
|      |           | 스크립트명 또는 "모델" | | |

검증 방법: 사용자가 스스로 확인할 수 있는 명령/경로 1~3개
```

**판정 주체 열이 비어 있으면 그 줄은 검증된 적이 없다.** 스크립트가 정했으면
스크립트 이름과 exit code 를, 모델이 정했으면 "모델" 이라고 적는다.

## § 6 — 안티패턴

- ❌ 기준 없이 루프 시작 — 먼저 기준부터 확정한다
- ❌ 채점만 하고 안 고침 / 고치고 재채점 안 함 — 4단계는 세트다
- ❌ 1회차에 전 기준 9~10점 — 기준이 느슨하다는 신호. 기준을 다시 엄격하게 세운다
- ❌ 최저 점수를 놔두고 이미 높은 항목을 다듬음 — 항상 최저부터
- ❌ 중단 조건 도달 후 "조금만 더" — 5회차/무진전 2회면 무조건 멈추고 보고
- ❌ **증거 없이 재작성** — 결함 티켓이 없으면 그 부분은 보존한다 (§ 2.1)
- ❌ **회차마다 전체 맥락 재주입** — 넣을 것은 넷뿐이다 (§ 2.2)
- ❌ **스크립트가 판정 가능한 기준을 눈으로 채점** — 먼저 돌려보고 exit code 를 쓴다
- ❌ **보류를 실패로 기록** — 권한·데이터·결정 부재는 고칠 대상이 아니라 받아올 대상이다 (§ 4.2)
- ❌ **정책 게이트 `exit 2` 를 점수로 덮기** — 전 기준 10점이어도 완료가 아니다
